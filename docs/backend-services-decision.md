## Deployment boundaries

Use local development services and separate hosted staging/production Supabase projects and Render services. Never share production credentials or private data with staging. Keep local development free of cloud compute charges where possible. Render's free web service can support disposable previews, but is not the production baseline.

Before deployment, add reproducible build/start commands that read hosting-provided environment variables without requiring a local `.env` file (the current API start command requires one). Bind `HOST=0.0.0.0`, accept the host's `PORT`, configure secrets, use `/ready` for health checks, and verify proxy/rate-limit behavior. Existing entry points are `apps/api/package.json:8`, `apps/api/src/server.ts:8`, `apps/api/src/server.ts:9`, and `apps/api/src/app.ts:86`. Deployment configuration, worker implementation and monitoring remain later tasks.

## Capability references and validation

- [Supabase Queues](https://supabase.com/docs/guides/queues): PostgreSQL-backed durable queue with visibility-window delivery semantics. Do not interpret this as exactly-once execution of external effects.
- [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/): persistent local database across app restarts; use the version compatible with the selected Expo SDK when implementing it.
- [Render regions](https://render.com/docs/regions): Virginia is available; confirm placement when provisioning.

Validation: inspected existing dependency declarations, API client/authentication flow, SQL migration and server configuration; checked official capability/pricing sources and the estimate arithmetic. Documentation-only selection: no runtime changes, service creation, dependency installation or cloud deployment was performed.
